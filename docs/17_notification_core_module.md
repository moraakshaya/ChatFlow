# 📌 Overview

The **Notification Core module** introduces a centralized notification system for the chat platform.

The purpose of this module is to create and manage notifications generated by important application events such as:

* New messages
* Message mentions
* Message reactions
* Future system events

Notifications are persisted in MongoDB so they remain available even when the recipient is offline.

Socket.IO is then used to deliver newly created notifications instantly when the recipient is connected.

The architecture separates:

* Application events
* Notification processing
* Persistent storage
* Real-time delivery

```text
                  Application Event
                         │
                         ▼
                 Notification Service
                         │
                         ▼
                      MongoDB
                         │
                  Save Successful
                         │
                         ▼
                     Socket.IO
                         │
                         ▼
                        User
```

---

# 🎯 Objectives

The Notification Core module should:

* Create notifications internally through the Notification Service
* Store notifications in MongoDB
* Retrieve notifications
* Retrieve individual notifications
* Mark notifications as read
* Mark all notifications as read
* Delete notifications when required
* Deliver notifications through Socket.IO
* Support different notification types
* Associate notifications with conversations/messages where applicable
* Distinguish notification recipients from event actors
* Ensure users only access their own notifications
* Reuse existing authentication and authorization
* Work correctly when users are offline
* Support multiple connected devices
* Prevent accidental duplicate notifications where necessary
* Provide a foundation for unread counters

---

# 🧠 Core Principle

Notifications have two responsibilities:

```text
Persistent Notification
        │
        ▼
     MongoDB
```

and:

```text
Real-Time Delivery
        │
        ▼
     Socket.IO
```

Therefore:

```text
Notification
     │
     ├── Store → MongoDB
     │
     └── Deliver → Socket.IO
```

The key rule is:

> **MongoDB is the source of truth. Socket.IO is only the real-time delivery layer.**

Socket.IO availability or user online status must never determine whether a notification is persisted.

# 🔄 Persistence Before Delivery

The Notification Core module follows a **persist-first delivery strategy**.

```text
Application Event
       │
       ▼
Notification Service
       │
       ▼
Validate Event
       │
       ▼
Determine Recipient
       │
       ▼
Determine Actor
       │
       ▼
Apply Notification Rules
       │
       ▼
Create Notification
       │
       ▼
MongoDB Save
       │
       ├───────────────┐
       │               │
      FAIL          SUCCESS
       │               │
       ▼               ▼
   Return Error     Socket.IO
                       │
                       ▼
                notification:new
```

### Why persist first?

Consider:

```text
MongoDB      ❌
Socket.IO    ❌
```

The notification should not be considered successfully created.

But:

```text
MongoDB      ✅
Socket.IO    ❌
```

The notification **has still been successfully created**.

The user can retrieve it later through:

```text
GET /api/notifications
```

Therefore:

> **Real-time delivery failure must not invalidate successful notification persistence.**

This is especially important for offline users and temporary Socket.IO disconnections.

# 🧩 Application Event vs Socket.IO Event

The Notification Core module distinguishes between **application/domain events** and **Socket.IO delivery events**.

## Application Event

Represents:

```text
Something happened in the application.
```

Examples:

```text
message.created
mention.created
reaction.created
```

These events are consumed by backend services.

---

## Socket.IO Event

Represents:

```text
Deliver something to a connected client.
```

Examples:

```text
message:new
reaction:added
notification:new
```

These are transport-level events.

Therefore:

```text
Application Event
       │
       ├── Notification Service
       │
       └── Other Backend Consumers
```

while:

```text
Socket.IO Event
       │
       └── Connected Clients
```

The Notification Service must **not depend on receiving Socket.IO delivery events**.

---

# 🔄 Notification Flow

Example:

User A sends a message to User B.

```text
User A
   │
   ▼
Message Service
   │
   ├── Persist Message
   │
   ├── message:new → User B if connected
   │
   └── message.created
             │
             ▼
      Notification Service
             │
             ├── Determine Recipient
             ├── Determine Actor
             ├── Check Rules
             └── Create Notification
                       │
                       ▼
                    MongoDB
                       │
                 Save Successful
                       │
                       ▼
                   Socket.IO
                       │
                       ▼
                    User B
                       │
                       ▼
                Notification UI
```

The important distinction is:

```text
message.created
      =
Application Event
```

while:

```text
message:new
      =
Socket.IO Delivery Event
```

The Notification Service consumes:

```text
message.created
```

not:

```text
message:new
```

# 📊 Field Definitions

| Field           | Type     | Required | Purpose                      |
| --------------- | -------- | -------: | ---------------------------- |
| `_id`           | ObjectId |      Yes | Notification identifier      |
| `recipient`     | ObjectId |      Yes | User receiving notification  |
| `type`          | String   |      Yes | Notification type            |
| `title`         | String   |      Yes | Notification title           |
| `message`       | String   |      Yes | Notification content         |
| `conversation`  | ObjectId |       No | Related conversation         |
| `sourceMessage` | ObjectId |       No | Related message              |
| `actor`         | ObjectId |       No | User who triggered the event |
| `isRead`        | Boolean  |      Yes | Read state                   |
| `createdAt`     | Date     |      Yes | Creation timestamp           |
| `updatedAt`     | Date     |      Yes | Update timestamp             |

---

# 👤 Actor Field

The `actor` field is intentionally optional.

For the current notification types:

```text
MESSAGE
MENTION
REACTION
```

there will normally be a human actor.

Example:

```javascript
{
    "actor": "68user123",
    "recipient": "68user456"
}
```

However, future system-generated notifications may not have a human actor.

For example:

```text
System
   │
   ▼
Security Notification
```

or:

```text
Organization
   │
   ▼
System Notification
```

Therefore:

```text
actor: ObjectId
required: false
```

is intentional.

---

# 👤 Recipient vs Actor

These fields have different purposes.

### Recipient

The user receiving the notification:

```text
recipient = User B
```

### Actor

The user who caused the event:

```text
actor = User A
```

Example:

```text
User A reacts ❤️
        │
        ▼
Notification
        │
        ├── actor = User A
        └── recipient = Message Owner
```

This distinction makes the notification system reusable.

# 🧠 Optional Relationships

`conversation` and `sourceMessage` are intentionally optional.

Current notifications may reference:

```text
Conversation
Message
```

but future notifications may not.

For example:

```text
system
security
organization
```

could be notification types that do not belong to a specific conversation or message.

Therefore the model does not force:

```text
conversation
sourceMessage
```

to exist for every notification.

---

# 🚫 Self Notifications

Generally, a user should not receive a notification for their own action.

Example:

```text
User A sends message
        │
        ▼
User A
```

Do not create:

```text
User A → "You sent a message"
```

Similarly:

```text
User A reacts to own message
```

should normally not create a reaction notification for User A.

Conceptually:

```text
actor === recipient
        │
        ▼
Skip notification
```

unless a future product requirement explicitly enables self-notifications.

---

# 🔁 Duplicate Notification Handling

Duplicate notification events should be handled where necessary.

For the portfolio version, the system does not require:

* Redis
* Kafka
* RabbitMQ
* Distributed idempotency infrastructure

Instead, notification-generating events should use their source identity when practical.

Examples:

```text
messageId
reactionId
eventId
```

Conceptually:

```text
Notification Event
       │
       ▼
Check Source Identity
       │
       ├── Already processed → Skip
       │
       └── New event → Create
```

For example, a reaction notification can use:

```text
reactionId
+
recipient
```

to prevent accidental duplicate notification creation.

The exact uniqueness strategy can vary by notification type.

Advanced distributed idempotency can be introduced later if the system requires it.

### User-Facing Notification Operations


# 🧠 Why Use a Service?

Without a service:

```text
Message Controller
Reaction Controller
Mention Controller
```

could each contain notification logic.

That creates duplication.

Instead:

```text
Message Service ──────┐

Mention Service ───────┘
```

This centralizes:

```text

Self-notification rules
Notification creation

```

# 👤 User-Specific Socket Room

Unlike conversation events, notifications should be sent to a **user-specific room**.

Recommended:

```text
user:{userId}
```

Example:

```text
user:68user456
```

When a user connects:

```text
Socket
  │
  ▼
Authenticate
  │
  ▼
Join user room
  │
  ▼
user:68user456
```

Then:

```javascript
io.to(`user:${recipientId}`)
    .emit("notification:new", payload);
```

This ensures the notification is delivered only to the intended user.

# ⚠️ Socket.IO Delivery Failure

Socket.IO delivery is **best-effort real-time delivery**.

If:

```text
MongoDB      ✅
Socket.IO    ❌
```

the notification remains successfully stored.

The user can later retrieve it using:

```http
GET /api/notifications
```

Therefore:

```text
Socket.IO Failure
      ≠
Notification Creation Failure
```

This maintains MongoDB as the source of truth.

For the portfolio version, no additional message broker or delivery retry system is required.

# 🔐 Authorization

Every notification API must use the authenticated user.

For example:

```http
GET /api/notifications
Authorization: Bearer <token>
```

The backend obtains:

```text
req.user.userId
```

and retrieves:

```text
notifications.recipient === req.user.userId
```

The client must not control the recipient.

---

# 🚫 Notification ID Authorization

User A should not be able to access User B's notification.

Example:

```text
User A
   │
   ▼
GET /api/notifications/User-B-notification
```

The server verifies:

```text
notification.recipient
        ===
authenticatedUserId
```

If ownership fails, the API may return:

```text
403 Forbidden
```

or:

```text
404 Not Found
```

depending on the API's chosen security strategy.

For security-sensitive resource lookups, returning `404` can avoid revealing whether another user's notification exists.

---

# 🛡️ Security Rules

The backend must enforce:

```text
Authenticated User
        │
        ▼
Own Notifications Only
```

Never trust:

```javascript
{
    "recipient": "another-user"
}
```

from the client.

The recipient is determined by trusted backend/application logic.

Notifications may reference documents that are later deleted.

Examples:

```text
Notification
     │
     ├── sourceMessage → deleted
     └── conversation → deleted
```

For the portfolio version, the notification itself should normally remain.

Conceptually:

```text
Referenced document deleted
        │
        ▼
Notification remains
        │
        ▼
UI detects unavailable reference
        │
        ▼
Gracefully displays unavailable content
```

For example:

```text

```

The module does not need a complex notification cleanup engine.

Similarly, if the actor user is later deleted, the notification can remain while the UI gracefully handles the missing actor.

Notifications should not depend on a particular communication transport.

The same Notification Service can conceptually be triggered through:

```text

        │
        ▼

        │
        ▼
```



# 🏁 Summary

The **Notification Core module** provides the foundation for the notification system.

Its architecture follows a simple and scalable principle:

> **MongoDB stores notifications; Socket.IO delivers them instantly.**

The module supports:

```text
Messages
Reactions
Mentions
     │
     ▼
Application Events
     │
     ▼
Notification Service
     │
     ├── MongoDB
     │
     └── Socket.IO
```

The design intentionally separates:

```text
Application Event
        │
        └── Describes what happened

Notification Service
        │
        └── Decides whether a notification should exist

MongoDB
        │
        └── Stores persistent notification state

Socket.IO
        │
        └── Delivers notifications in real time
```

The key principles are:

> **MongoDB is the source of truth for notifications.**

> **Notification persistence does not depend on Socket.IO or user online status.**

> **Notifications are persisted before Socket.IO delivery is attempted.**

> **A Socket.IO delivery failure does not invalidate a successfully persisted notification.**

> **Application events trigger notification processing; Socket.IO events only deliver data to connected clients.**

> **`recipient` identifies who receives the notification, while `actor` identifies who caused the event.**

> **The `actor` field is optional to support future system-generated notifications.**

> **Conversation and message references are optional so future notification types are not forced to belong to a chat message.**

> **A public client-facing notification creation endpoint is not required; notifications are created through the Notification Service.**

> **Duplicate notification events should use their originating event identity where necessary to avoid accidental duplicate creation.**

> **Deleted referenced documents do not require notification deletion; the notification remains and the UI handles unavailable references gracefully.**

> **Self-notifications are prevented by default unless explicitly required by a future product decision.**

> **The Notification Service remains independent of Socket.IO delivery events.**
